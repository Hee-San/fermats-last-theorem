Lean 4 におけるフェルマーの最終定理

Mathlib の上に構築された、Lean 4 による機械検証済みのフェルマーの最終定理の完全な証明です（Lean 4.33.1、Mathlib v4.33.0、lakefile.lean でコミットを固定）。議論は Frey・Serre・Ribet・Wiles・Taylor–Wiles のものです。PROOF-PATH.md は各ステップとそれを担う Lean の定理を挙げ、html/ フォルダは証明全体をオフラインで閲覧できる Web ページとして提示します（下の「ブラウザで証明を読む」を参照）。

研究用の成果物です。保守されておらず、貢献も受け付けていません。

主張

Theorems/Thm_fermat_last_theorem.lean は

theorem fermat_last_theorem (n : ℕ) (hn : 3 ≤ n) (a b c : ℕ) (ha : 0 < a) (hb : 0 < b) (hc : 0 < c) : a ^ n + b ^ n ≠ c ^ n

を宣言し、既定のビルド対象 FinalCheck.lean は

/-- info: 'fermat_last_theorem' depends on axioms: [propext, Classical.choice, Quot.sound] -/
#guard_msgs in
#print axioms fermat_last_theorem

を含みます。したがって、証明が Lean の標準的な三つの公理だけに依存していなければビルドは失敗します（sorry なし、追加の axiom なし、native_decide なし）。FinalCheck.lean はまた、この定理から Mathlib 自身の主張 FermatLastTheorem を導出します。

どのように検証されたか

  • ビルド。Lean 4.33.1（2026 年のカーネルの健全性修正を含む）上で、Mathlib をソースからコンパイルしつつ、ゼロから lake build を行いました。このリポジトリの 60,475 モジュールすべてがビルドされ、すべての宣言が Lean のカーネルによって検査され、公理は上記のとおりでした。
  • comparator。leanprover/comparator v4.33.0 が、Mathlib だけを使って定理を述べた verification/comparator/Challenge.lean に対してビルドを検査しました。証明された主張とそれが言及するすべての定数がチャレンジと同一であること、他の公理が使われていないこと、そして Mathlib を含む証明全体が Lean のカーネルで再生されることを確認しました。判定：Your solution is okay!
  • 第二のカーネル。Rust で書かれた独立の Lean カーネルである nanoda 0.4.13 が、同じ環境のエクスポート（lean4export で書き出したもの）を受理しました：Checked 1052234 declarations with no errors。nanoda は自前の四つの小さなパッチ（verification/nanoda/patches/）を当ててビルドしました。一つは進捗出力を加えるもので、三つは定義的等価性の探索を高速化するものです。後者がないと、この証明のいくつかの宣言は無改変の nanoda を一つあたり何時間も占有します。どのパッチも型付け規則を追加・削除・弱体化しません。

どのモジュールも axiom、sorry、native_decide、unsafe、extern、implemented_by、partial def、#eval を含みません（Challenge.lean は設計上 sorry を使いますが、パッケージの一部ではありません）。

これらの検査を合わせると、Lean のカーネル（または nanoda）と検査ツールを信頼するかぎり、上の主張が三つの公理から従うことが確立されます。主張は Lean 組み込みの自然数、+、≤、<、≠ で書かれており、Mathlib 由来の唯一の材料は ℕ 上の ^ ですが、Mathlib はこれを Lean 組み込みの冪として定義しており、comparator は主張が言及するすべての定義が素の Mathlib のものと同一であることを検査します。Mathlib の他の部分を信頼する必要はありません。主張の下にあるすべてをカーネルが検査するからです。どのツールにも検査できないのは、各中間定理がその名前の示唆する意味をもつかどうかです。それは読者が判断することであり、PROOF-PATH.md は各ステップの背後にある Lean の定理を挙げ、名前のついた各古典的結果がここでどの程度の強さで証明されているかを正確に述べています。

ブラウザで証明を読む

html/ フォルダ（約 390 MB）は、このリポジトリを静的な Web ページとして提示します。証明の道筋を一歩ずつ。29,511 個の定理それぞれのページ（Lean の正確な命題、引用するものと引用されるもの、展開できる依存グラフ）と、1,450 個の定義モジュールそれぞれのページ（全ソースと、それを使う命題）。すべての定理名・定義名にわたる検索ボックス。ランドマーク定理のグラフ。そして相互リンクつきで表示された README.md、PROOF-PATH.md、ATTRIBUTION.md。このフォルダはリポジトリの一部なので、クローンや ZIP ダウンロードにはすでに含まれています（html/ を別のアーカイブとして入手した場合は、リポジトリの直下に展開してください）。html/index.html を Web ブラウザで開いてください。すべてオフラインで、Web サーバーなしで動きます。ページは Chromium 系ブラウザでのみ機械的にテストされており、html/README-DOCS.md が、何が Lean ファイルからの引用で何が生成されたものかを説明しています（英語の要約と参考文献の提案は自動生成されたもので、Lean の命題文が正です）。概要・証明の道筋・ランドマーク図・About の日本語版は html/ja/index.html にあります。

自分で検査する

  • Linux または macOS（Windows にはパスが長すぎるものがあります）、elan（lean-toolchain から Lean 4.33.1 をインストールします）、そしてネットワーク接続が必要です。Lake は GitHub から Mathlib を取得してソースからコンパイルします。このツールチェインに合うビルド済み Mathlib がないためです（96 ジョブで約 13 分）。
  • ビルドには並列ジョブあたり約 5 GB のメモリが必要です（いくつかのモジュールは最大 36 GB を要します）。.lake/ の下に約 67 GB のディスク、加えてビルドの進行にあわせて削除できる C ファイル（約 220 GB）。我々のビルドは 96 ジョブで 5 時間 32 分、メモリのピークは 153 GB でした。
  • comparator は約 15 時間かかり（我々の場合 14 時間 46 分）、そのほとんどは 1 コアでのカーネル再生です。メモリのピークは 230 GB だったので、300 GB を見込んでください。nanoda は comparator のスクリプトのあとに実行してください（そのツールを再利用します）。37.8 GB のエクスポートの書き出しには約 90 GB のメモリで 1 時間、検査自体は約 40 GB（16 スレッドで約 30 分）かかります。どちらのスクリプトも Linux 用です（bash、git、python3、GNU coreutils。nanoda はさらに patch、cargo、crates.io を必要とします）。
git clone <this repository> flt && cd flt
LEAN_NUM_THREADS=96 lake build              # 既定ではハードウェアスレッドごとに 1 ジョブ。メモリを抑えるには下げる（ジョブあたり約 5 GB）
verification/comparator/run.sh              # 判定：.verify-work/wrapper/comparator.log の最終行
verification/nanoda/run.sh                  # comparator のスクリプトのあとに実行。判定：.verify-work/nanoda/run-*/nanoda.stdout

Lean はビルド中に大量の非推奨警告とスタイルリンターの警告を出力します。結果には影響しません。出力が 'flt_mathlib' depends on axioms: [propext, Classical.choice, Quot.sound] と Build completed successfully で終われば、ビルドは成功です。各スクリプトは固定されたバージョンの検査器を取得してビルドし、成功時に 0 で終了します。

ソースについて

FinalCheck.lean が既定の対象です。Theorems/ は命題を、P2M/Sol/ は証明を（それぞれ引用する命題をインポートします）、Definitions/ は定義を、verification/ は二つの検査を、html/ は上述の Web ページを、tools/docs-site/ はそれを生成したプログラムを収めています。Lean ソースは、人間が書いたオープンソースの Lean の上に、Lean を裁定者として AI エージェントが構築したもので、読まれるためではなく検査されるために書かれています。名前は機械生成で、P2M や 16 進の接尾辞といったラベルは数学ではなくパイプラインのラベルであり、名前と命題が食い違うときは命題のほうが証明されたものです。上流の告知、doc string と引用（ATTRIBUTION.md に列挙）、そして #guard_msgs が検査する期待出力のコメントを除き、コメントは削除されています。
